# Releasing Hardless

A release is one version number for everything: the `hardless` binary, the crates, the npm
packages, the Docker image and the Chrome extension. Pushing a `vX.Y.Z` tag starts
[`.github/workflows/release.yml`](.github/workflows/release.yml) (generated by cargo-dist from
[`dist-workspace.toml`](dist-workspace.toml)), which:

1. builds `hardless` for Windows, macOS and Linux (glibc and static musl), on x86_64 and arm64,
   with shell and PowerShell installers and a Homebrew formula;
2. creates the GitHub Release with those files and their SHA-256 checksums;
3. publishes, in parallel: the formula to `hardlessdev/homebrew-tap`, the crates to crates.io
   ([`publish-crates.yml`](.github/workflows/publish-crates.yml)), `@hardless/types`,
   `@hardless/shim-web`, `@hardless/playwright` and `hardless` to npm
   ([`publish-npm.yml`](.github/workflows/publish-npm.yml)) and `hardless/hardless` to Docker
   Hub ([`publish-docker.yml`](.github/workflows/publish-docker.yml));
4. attaches `hardless-extension-X.Y.Z.zip` to the release
   ([`publish-extension.yml`](.github/workflows/publish-extension.yml)).

Every pull request runs steps 1 and the checks of step 3 without publishing anything: cargo-dist
builds all eight platforms, and CI's "Release dry run" job runs `cargo publish --dry-run`,
packs and checks the npm tarballs (`scripts/pack-npm.mjs`, `npm publish --dry-run`) and zips the
extension.

## One-time setup (maintainer only)

Tokens go straight from each site into GitHub's secret settings. Never paste them anywhere else.

1. **GitHub environment.** In the repository's Settings → Environments, create `release`. Add
   yourself as a required reviewer, so every publish waits for your approval.
2. **crates.io.** Sign in with GitHub, then Account Settings → API Tokens → New Token, with the
   scopes `publish-new` and `publish-update` and the crate pattern `hardless*`. Save it as the
   `release` environment secret `CARGO_REGISTRY_TOKEN`.
3. **npm.** In the npm account that owns the `hardless` org: Access Tokens → Generate New Token
   → Granular Access Token, with read and write access to all packages (the unscoped `hardless`
   package does not exist yet, so it cannot be selected) and "bypass two-factor authentication"
   enabled for automation. Save it as the `release` environment secret `NPM_TOKEN`.
4. **Docker Hub.** In the `hardless` account: Account settings → Personal access tokens → a
   Read & Write token. Save it as the `release` environment secret `DOCKERHUB_TOKEN`, and the
   account name `hardless` as the `release` environment variable `DOCKERHUB_USERNAME`.
5. **Homebrew tap.** Create the public repository `hardlessdev/homebrew-tap` (a README is
   enough). Create a fine-grained personal access token with "Contents: read and write" on that
   repository only. Save it as the **repository** secret `HOMEBREW_TAP_TOKEN` (the generated
   Homebrew job does not use the `release` environment).

After the first release, switch crates.io and npm to trusted publishing, so no long-lived
token is stored. The publish workflows use trusted publishing whenever the token secret is
absent. Both sites match the top-level workflow, `release.yml`, not the reusable one it calls.

- **crates.io** (done on 23 Oct 2026): each crate's settings page has two GitHub trusted
  publishers for `hardlessdev/hardless`, environment `release`: one for `release.yml` and
  one for `publish-crates.yml` (for finishing a publish by hand). `CARGO_REGISTRY_TOKEN` is
  deleted and revoked.
- **npm** (not yet): a new npm trusted publisher expires if it is not used to publish within
  2 days, so set it up **just before** a release. On each package's settings page (Trusted
  Publisher → GitHub Actions): organization `hardlessdev`, repository `hardless`, workflow
  `release.yml`, environment `release`, and under **Allowed actions** tick `npm publish` (by
  default only staging is allowed). Delete `NPM_TOKEN` from the `release` environment in the
  same sitting, so the release uses the new publishers. After that release succeeds, revoke
  the npm token and select "Require two-factor authentication and disallow tokens" on each
  package.

## Making a release

0. Until npm uses trusted publishing (above), set it up right before releasing, or make
   sure `NPM_TOKEN` has not expired (it was created with a 30-day expiry on 21 Oct 2026).
1. On a branch, set the version and write the changelogs:

   ```sh
   pnpm changeset version              # npm changelogs from .changeset/, bumps the packages
   node scripts/set-version.mjs 0.1.0  # crates, every package.json, the extension manifest
   cargo update --workspace            # Cargo.lock
   ```

   Add a `## 0.1.0 - YYYY-MM-DD` section to [`CHANGELOG.md`](CHANGELOG.md): cargo-dist uses it
   as the GitHub Release notes.

2. Commit as `chore(release): v0.1.0`, open a pull request and wait for CI, including the
   cargo-dist builds and the release dry run.
3. Merge it, then tag the merge commit and push the tag:

   ```sh
   git tag v0.1.0
   git push origin v0.1.0
   ```

4. Approve the `release` environment when GitHub asks, and watch the Release workflow.
5. Check the result: `npx hardless@0.1.0 --version`,
   `docker run --rm hardless/hardless:0.1.0 --version`,
   `brew install hardlessdev/tap/hardless`, the installers on the release page, and that the
   extension zip loads unpacked in Chrome.
6. Re-deploy the docs site (`npm run deploy` in `hardless-docs`).

If a publish job fails after others succeeded, fix the cause, then re-run only the failed
jobs from the workflow run page. crates.io and npm never accept the same version twice, so do
not re-tag. Re-runs use the workflow files of the tag, so a fix to a workflow cannot reach
them; for that case, Publish crates and Publish Chrome extension zip can be run by hand
(Actions → the workflow → Run workflow, with the tag) from `main`, provided the crates or the
extension are unchanged since the tag (they check). The crates job skips crates already on
crates.io and waits out crates.io's limit on new crates (a first release of many crates hits
it). Running Publish crates by hand needs the `release` environment to allow `main` for that
run: add `main` under its deployment branches, and remove it afterwards.
